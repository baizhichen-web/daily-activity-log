# 累计审计规则（rules）

> 同一问题出现 ≥2 次时提炼为规则，成为每次审计的必查项。首次规则集由 2026-08-14 勘察建立。
> **Evolution 视角（P3，2026-08-24 起）**：本文件与 pitfalls.md 共同构成工作空间的 **Gene 库**——单行「触发条件→动作」即紧凑基因；每次审计输出 rule 回执（哪些问题被既有 rule 避免/检出），新增条目须为紧凑单行格式。

- R-001 根目录不得出现规范外的散落文件；新文件必须先判断归属目录（studio/projects、ops/reports、temp/ 等）再落盘。
- R-002 看板快照超过 3 天必须提示刷新；审计中快照过期时报告必须标注「快照过期」。
- R-003 ~~`ops/logs/` 无近期日志 = bridge 未运行或日志路径漂移，必须上报~~ → **修订（2026-08-14）**：`ops/logs/` 无近期日志 ≠ bridge 未运行——bridge 日志实际落盘于 `~/.lark-channel/profiles/*/logs/`（`LARK_CHANNEL_HOME`）；先查该处与 node 进程，再定性；规范文件中的路径描述过时本身也是一条发现。
- R-004 工具调用失败（lark-cli、git、node）必须如实上报，不静默降级、不假装成功。
- R-005 **看板 ↔ studio/projects 双向核对（新增，2026-08-14）**：目录有但看板无记录、或看板有但目录无的项目，必须列出待用户确认（实例：text-catcher、认知外包、Figma-Agent 打通）。
- R-006 **插件平面判据（新增，2026-08-14）**：inject host 服务或监听 root 级事件（`agent/created` 等）的插件必须放 host 组合（`~/.dsh/profiles/web/cordis.patch.yml`）；preset 行只放消费 host registry 且不依赖 root 事件的行。standingKeyFor 通过 ≠ 功能生效（实例：dsh-schedule 放 preset 挂载成功但工具从未注入）。
- R-007 **有产出的工作必须立项（新增，2026-08-15）**：产出文档/插件/可复用工作模式/系统性方案 → `studio/projects/<name>/`（README + AGENTS.md）+ 飞书看板登记；临时小事不必。审计时检查「散落工作」：发现未立项的有产出工作必须列出（实例：workspace-auditor 08-14 建立，08-15 才补立项；根 AGENTS.md 核心规则已同步）。
- R-008 **安装与持久性系统变更必先报批（新增，2026-08-17，源自用户口头立规，已入根 AGENTS.md 核心规则）**：pip/npm/全局工具/服务/计划任务/防火墙/ACL/开机自启等变更，先说明「装什么、装在哪、影响什么」、获批后再执行；只读检查与临时进程终止不受限。审计检查「近期系统变更是否有告知记录」（实例：2026-08-17 未经告知 pip 安装 rapidocr-onnxruntime，用户事后立规）。
- R-009 **第三方代码与运行时目录归属声明（新增，2026-08-18，源自整理专项 O-026/O-027）**：clone 的第三方仓库、插件运行时目录、调研素材，落盘前必须先声明归属（工作区外 `_third-party/`、temp/、或 .gitignore 忽略）；禁止默认落工作区根目录。运行时目录若因工具硬编码路径而无法移动（如 `.dsh-vision/`），必须立即补 .gitignore 并记录在 AGENTS.md temp/ 小节。审计时对根目录每个新增目录做溯源（mtime + 会话轨迹 + git ignore 状态）。
- R-010 **审计必查 wiki/log.md（新增，2026-08-18，源自整理专项教训）**：审计的日志维度以 `bAI/bAI/wiki/log.md` 为准绳——log.md 是知识/操作行为的权威摘要（notes/ 只是可选详细展开），检查某工作「有无记录」时**必须同时查 log.md 与 notes/**，只查 notes 会造成漏判（实例：archify 08-16 入库记录在 log.md 第 21 行，2026-08-18 首次审计误判为「无记录」）。审计台账自身也在本题范围内：审计执行的关键动作（归档、移动、裁决）应回写一行到 log.md，让状态流进 Obsidian。
- R-011 **文件处理优先转 Markdown（新增，2026-08-18，用户偏好立规）**：处理上传/引用的文件（pdf/docx/xlsx/pptx/图片等）时，**先转为 Markdown 再阅读/入库**——更适合知识库使用与阅读、节省 token、读取更精准。工具：本地 `markitdown` CLI（`markitdown <file> -o <file>.md`，2026-08-18 修复并升级 0.1.7，安装在 Python310 用户级）。转换产物放 `temp/` 或随项目；原文件仍按规范归档。审计检查：新增文件处理流程是否优先走 markitdown。
- R-012 **规范文件禁止手写「最后更新」日期行（新增，2026-08-24，源自瘦身与双库更新两起漏同步事故；此前 CLAUDE.md 挂 2026-08-02 死日期曾致「AGENTS.md 过时」误判）**：变更历史由 git log 与 wiki/log.md 承载；发现手写日期行必须提议删除。触发→动作：见规范文件尾部手写日期行 → 提议删除并留一行时效源声明。
- R-013 **新增组件必须登记注册表并做波及分析（新增，2026-08-24，源自 vault-search 上线六处补丁实践）**：任何新外挂组件上线 → 登记 `ops/components.md`（功能/接入形态/版本锁定/健康检查/回退/文档六字段）→ 输出波及清单（sensor/规范/动线/AGENTS 政策表）逐项处置。接入形态仅限 SKILL.md 或 MCP/本地服务两种。
- R-014 **git 文档/规范层堆积立案（新增，2026-09-07，O-004/O-030 两次复发 + 规范文件现行版未入库致回退保证落空；✅ 2026-09-08 用户确认转正式）**：触发→动作：git status 未提交 >30 条或跨度 >7 天 → 立案 open item，分主题提交且**规范与设计文件优先**；巡检管线自身产物（audit/board-reviews/log）随当日或当日巡检提交入库，不让治理文件累积为下一笔堆积。
