## 0. 定位与范围

把「学校微信群消息 → 个人事务系统」做成一条可复用的流水线。人只做一个动作（投消息），AI 负责其余全部（存、分、排、记、回执）。

**范围内**：班级群、学院通知等学校文本/图片/文件消息的投递→归档→排程→看板→指针卡→回执。
**范围外**：微信侧自动抓取（v1 人工；自动化走 §5 升级路径）；非学校消息（默认也兼容投进来，按同规则处理）；群聊内容写作/回复代发。

## 1. 数据模型：三处各一真身，杜绝双写

| 数据 | 唯一真身 | 别处只放 |
|---|---|---|
| 消息原文/附件 | `E:\Desktop\学业与申请\消息中台\`（卡+文件） | 指针卡（摘要+路径）→ bAI raw |
| 行动项（截止/任务） | 飞书日程 + 工作空间看板 | 卡片「处理」字段记 event/record id |
| 项目状态 | 飞书看板 | AGENTS.md 不写状态值 |

飞书群是**传输通道**，不是存储层；飞书消息本身可撤回可过期，落卡才算数。

## 2. 消息卡规范 v0.1

### 2.1 两级卡：批次卡默认，要事升单卡

合并转发一晚可能带回 5-10 条消息，逐条建文件会碎片化。规范：

- **批次卡**：每晚合并转发 → 一张批次卡，放 `00_收件箱/`，文件名 `YYYY-MM-DD-夜集.md`（日期=收件日）。每条消息一个条目，格式见 2.3。
- **升级单卡**：凡「⚠️ 有截止」「参考（值得回看）」「带附件/截图」的条目，从批次卡拆出独立卡，移入对应分类目录，批次卡该条目尾注 `→ 已升卡 文件名`。
- **单发**（⚠️ 紧急当场投的）：直接建单卡进对应目录。

### 2.2 单卡模板（README 速查版同步）

```markdown
# YYYY-MM-DD 来源群 | 主题
- 紧急度：⚠️ 有截止 / 常规 / 参考
- 来源：群名（发送人）；批次：MM-DD夜集 / ⚠️单发
- 原文：（文本直接贴；文件/截图放同目录，此处写文件名）
- 截止时间：（精确到 HH:MM；「周几前」类换算后标注推算依据；无则 —）
- 处理：归档 ☑ / 日程（日期+标题）/ 看板（record id）/ 指针卡（raw 路径）
- 备注：
```

### 2.3 条目格式（批次卡内）

```markdown
## HH:MM 来源群 | 主题        ← 微信卡片里有时间/发送人就照录
- 原文：…
- 判级：⚠️ / 常规 / 参考      ← AI 判级，见 §4.2
```

### 2.4 通用约定

- 文件名：`YYYY-MM-DD-主题.md`（附件为 `-主题.原扩展名`）；同日同主题加 `-2` 后缀；**文件名冲突处理遵循 `E:\AGENTS.md` 移动规范**（rename 前找空位，Windows 静默覆盖是已知坑）。
- 编码 UTF-8；卡内不写绝对盘符前缀以外的冗余路径（数据区相对路径即可）。
- 子目录（01-05）是临时脚手架：分类攒够了再调，AI 出增删合并建议、白纸点头才动。

## 3. SOP v1 定稿（人肉版）

1. **每晚 21:00 前 · 夜收件**：微信长按→多选当日消息→合并转发「文件传输助手」→ 电脑微信打开卡片→全选复制为纯文本→贴进飞书「自动化通知」群。最终落飞书必须是**摊平的文字**（AI 读不了微信卡片）；一条消息太长可分多条贴，群内不标特殊符号。
2. **⚠️ 紧急单发**：当场复制单条贴飞书群，消息最前面加一行 `⚠️`（口令唯一性见 D5）。不等夜收件。
3. **AI 处理时机**：夜收件后**同晚**由白纸上会话一句话触发（「处理收件」），或次晨由 9:00 晨间提醒顺带扫描（见 D2/D3）。SOP v1 阶段不做无人值守轮询。
4. **文件/图片类通知**：原件存数据区对应目录，卡内写文件名；截图无法转文字的，卡内保留图片文件名+AI 可读则补一句内容摘要。
5. **防漏兜底**：白纸哪天忘了投，AI 不猜；晨间回执固定含一句「昨日无投递/已处理 N 条」。

## 4. AI 处理承诺（收到 → 建卡 → 排程 → 回执）

### 4.1 四动作

| # | 动作 | 具体 | 失败时 |
|---|---|---|---|
| ① 存 | 逐条判级建卡（§2），落数据区目录 | 卡数=条数对账；`E:\Desktop\AI_itself` 是 git 仓库 → 按 D6 授权 commit（附变更文件数），不可回退即报警 | 上报，不静默丢条 |
| ② 排 | 有明确截止 → `lark-cli calendar +create` 建事件，重要节点带原生提醒（默认提前 1 天 + 当天早 9 点） | 日程记录 event id 写回卡片「处理」行 | 上报，卡片标「日程未建」 |
| ③ 挂 | 行动项挂工作空间看板：属开学季的并入 `recvtYye1BVt5j`/`recvtYyfETvb3R`「进度」字段（append，不覆盖原内容）；独立事务按 D4 处理 | 记 record id 回卡片 | 上报 |
| ④ 记 | 值得回看的 → bAI raw 建指针卡：frontmatter `source: E:\Desktop\学业与申请\消息中台\<相对路径>`，正文=摘要+原文件指针，**不复制全文** | 走 vault 现行 ingest 规范 | 跳过并在回执注明 |

### 4.2 判级规则（AI 先判，白纸可回改）

- **⚠️ 有截止**：含明确时间/「截止/前提交/尽快」字样 → 建卡+排程，回执置顶
- **常规**：知悉类（调课、后勤）→ 建卡归档，不排程
- **参考**：细则/办法/长篇（评奖细则、培养方案）→ 建卡+指针卡，不排程
- 拿不准按高一级处理（宁可多排一个日程，不漏一个截止）

### 4.3 回执格式（晨间提醒追加一节）

```
📥 消息桥：昨日处理 N 条（⚠️a / 常规b / 参考c）
　新建日程：…（日期 标题）
　更新看板：…（record）
　指针卡：…（N 张）
　⚠️ 待你确认：截止仅模糊/群名无法判断归属等存疑项
```

## 5. ClawBot 升级路径与复查节奏

**目标形态**：微信内把消息转发/直投给 Bot → 飞书群 → AI 处理，白纸零切换。

| 台阶 | 内容 | 触发条件 | 报批 |
|---|---|---|---|
| L0（现在） | SOP v1 人肉投递 | — | 否 |
| L1 | 直投：官方 `Tencent/openclaw-weixin` 支持群消息或将 Bot 加入转发列表（Issue #198） | 官方能力落地 + **安装 OpenClaw 报批**（含波及分析、登记 ops/components.md） | ✅ |
| L2 | 免会话：飞书事件订阅（复用 feishu-agent-bot 归档 OAuth 配置）→ 消息到群即触发 AI，替代「触发+轮询」 | L1 稳定或白纸想先自动化飞书侧；**注册常驻服务报批** | ✅ |
| 兜底 | wxauto UI 自动化监听群 | 官方路长期不通 + 白纸重新评估风险 | ✅（高风险档，默认排除） |

**复查节奏**：
- 会话顺检（每会话一次，只读 `gh api`）：只记异常，不写台账
- 每月巡检：查 `openclaw-weixin` releases / Issue #198 状态 / CHANGELOG 是否出现群聊字样，结果一行记入本文件 §10 巡检台账
- 命中升级条件 → 主动向白纸提请 L1/L2 报批，不自行装机

**巡检记录**：2026-09-03 Issue #198 open（2026-07-25 后无更新）；repo 活跃（9/1 发 v2.4.8，近期提交均为工程维护，README/CHANGELOG 未现群聊支持）。

## 7. 开工范围（评审通过后）

- **M0 · SOP 试运行 1-2 周（≈零代码）**：改数据区 README 定稿（含 D5 口令）、若 D3=A 则更新晨间 automation prompt、数据区 README 增补卡片规范。AI 按 §4 人肉触发跑真消息。
- **M1 · 工具收口**：处理链路稳定后，lark 读群/建日程/挂看板/落卡/回执写成一键脚本（`ops/scripts/` 或项目 `scripts/`），仍会话触发。
- **M2 · L2 事件订阅**：单独报批（装什么/装在哪/影响什么），批了才做。
- 每阶段：看板更新进度 + notes 迭代日志。

## 8. 风险清单

1. 人工投递本身会漏（忘了转/忘了贴）→ 靠晨间回执暴露，不假设有兜底
2. 合并转发复制丢信息（图片、小程序卡片复制不出）→ 走 §3 第 4 条文件规则
3. 判级误杀（截止漏判）→ §4.2 宁高勿低 + 回执存疑项
4. 飞书群误贴非消息内容（测试、闲聊）→ AI 按「常规」归档不排程，回执列出，白纸可删卡
5. ClawBot 长期不成熟 → 流水线不依赖它，L0 永远可用（升级是体验增益，不是地基）

## 9. 明确不做

协议/hook 微信自动化；未报批的装机与常驻服务；知识库全文复制；把 00_Inbox/消息中台混用（学业消息落点=消息中台，全局杂项=00_Inbox）。
