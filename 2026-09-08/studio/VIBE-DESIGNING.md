### 1.3 设计段两步制 —— 低保真 → 高保真（2026-08-25 站点实战复盘写回，作者定稿）

> 背景：resume-portfolio 首轮实现跳过了设计稿直接写代码，视觉决策被藏进 CSS 未经评审（作者指出「为什么不现在画布工具中设计」）。复盘定稿如下流程。

**六步全流程**（任何新页面/新区块适用）：

```
① 定向    参考采集 → 基因库（design/设计基因库.md）→ 总基调     【已完成过一次，增量维护】
② 低保真  **全要素静态稿**：布局/字体/配色/组件/真实文案全部到位，
          唯二从简 = 图片用占位框、无动效交互                        【画板稿：Pixso 优先，HTML 兜底】
③ 高保真  在②之上补齐：真实图片素材（Eagle 调取）+ 动效与交互状态
          （悬停/滚动/边界态），每张稿标注所用基因（G-xx）           【画板稿：Pixso 优先，HTML 兜底】
④ 评审    作者看稿批注 → 定稿 → 写回设计声明           【不通过则回②或③】
⑤ 实现    代码按稿换皮（数据驱动底层不动，改样式与布局层）
⑥ 验收    实现截图 vs ③高保真稿并排比对（chrome-devtools-mcp 自动化）
```

**三条硬规则**：
1. **先稿后码**——新页面/新区块必须先过②③④再写代码，除非作者明说「直接写」
2. **稿=验收唯一基准**——⑥的比对对象是③的高保真稿，不是参考站也不是记忆
3. **基因封闭**——设计稿里不允许出现基因库没有的视觉决策；要新决策，先进基因库再上稿

**既有实现的补票**：跳过流程的存量代码降级为「骨架草稿」，数据层/区块架构保留，视觉层回②③补票后重构。

**介质备注（2026-08-25 实测 + 作者裁决）**：Paper 免费档有**周配额**（MCP 调用次数，耗尽后提示数日重置）——**作者裁决：配额模型无法支撑免费设计，Paper 暂停使用**。设计稿介质改为 **HTML mockup + chrome-devtools-mcp 截图评审**（若对象本身是网页，站点实现即低保真稿；交付 = PNG 归档到项目 design/ + 可双击打开的自包含预览 HTML）。备选方案观察中：微信文章《SnAaFKvu8YiLLRHP89Z26w》（raw/ 有存档）、或实现外包 Codex（需交接文档）。Paper 若升级 Pro 或配额模型改变可复评。另：MCP 写入与桌面端存在同步回滚风险，**每轮设计稿交付须同时归档 PNG 到项目 design/**。

### 1.4 多会话协同约定（2026-08-25 新增，作者确认）

> 背景：两个设计会话并行期间已发生三次文件互覆（VIBE-DESIGNING 被改回旧版、memory 互写、Paper 同步回滚）。根因：共享文件「读整份→改→整份写回」，后写者赢。

**四条规则**：

1. **文件所有权制**——每个进行中的会话认领写区，互不重叠：
   - ZCode 会话：`site/` 代码、设计基因库、灵感库、Eagle、Pixso 画布
   - Codex 会话（若启用）：Figma 画布、其自有稿件
   - 交接或换手时在项目看板/交接文档登记
2. **共享文件只追加、不重写**——VIBE-DESIGNING（修订记录追加）、PRD（评审意见追加）、本文件体系各声明：改前必读最新版，只加自己的小节，不动他人段落
3. **git 小步提交**——每个会话收尾前必提交（工作空间是 git 仓，这是冲突保险）；原子改动原子提交
4. **一个时段一个活跃画布**——Pixso/Figma/HTML 不同时改同一设计；跨软件搬运只走文字层（Design.md / Components.md 是事实源，软件是渲染面），各软件实现同一份规范即不漂移

### 1.5 开工技术栈条款 —— AI 主动讲清选型（2026-08-28 新增，作者裁决）

> 背景：AIDesigning #6（Esther不二《为什么你vibecoding的项目很难维护》）指出 vibe coding 烂尾首因是 AI 默认把结构/样式/逻辑全塞进单文件 HTML。作者裁决时修正了视频的立场：**AI 的使用者往往不懂前端，所以义务在 AI 而不在使用者**——不是要求用户指定框架，而是 AI 必须主动讲清楚。

**条款**：

1. 重 UI / 网页项目开工时，AI **有义务用非工程师能懂的语言**主动讲清候选技术栈（框架、语言、构建工具）的优劣与本项目适配性，给出推荐及理由，由作者拍板后写入项目声明
2. AI **不得默默采用默认方案**开工，也**不得以「使用者未指定」为由甩锅**——讲清选型是开工的前置义务
3. **默认基线**：可长期维护的组件化工程（React/Vue + TypeScript + Vite 一类）；纯 HTML 单文件仅限小型一次性产物
4. 溯源印证：resume-portfolio 的 site/（vanilla）→ web/（React 18 + Vite 6 + TS）迁移（2026-08-25），作者确认迁移理由与视频同源——可维护性

## 第二章 设计哲学 —— 不变量 `初稿`

1. **契约层接受 UI/UX 验收的反向校验** —— 最小可用先行、真机验收、契约层为快速变更而设计（详见 L1：UI-DESIGN-PRINCIPLES.md）
2. **二创红线** —— 在原有功能上做；不许比原来难用、难看
3. **Design is the new code / GenUI is the new interface / Taste is the new engine**
4. **AI 管理优于刚性分类** —— 资产分类交给懂上下文的 AI，不预设受控词表
5. **薄在规则、厚在资产** —— 本文件只写可判错的条目；"什么是好"由 design/ 六级声明与 Eagle 库存承载

### 与项目的关系

- 项目内 `design/` 两件套**保留但角色调整**：EXECUTION-CONTRACT.md = 项目验收清单（Evaluator 的项目实例化）；原 DECLARATION 中**项目特有**的产品语义/领域语义 → 并入该项目的 Product/Domain 补充节，共性内容上浮到 studio/design/ 对应文件。迁移随各项目首次触达逐步进行，不一次性搬家。
- Eagle 是实体资产库存（组件参考/模板截图/素材）；studio/design/ 是规范文字；两者以链接互指。

## 第四章 设计流程 —— Design Skill `骨架待填`

四阶段各自的动作清单见 `design/skills/01~04`（骨架已建，逐阶段用真实任务填充）。总纲：

```
语境加载（Product/Domain + 相关 Components/Templates + Craft 反例）
→ 01 需求理解与规划（定义问题与验收标准）
→ 02 信息架构设计（结构与层级，Paper/Figma 出线框）
→ 03 页面组件设计（取件组装，Figma 高保真，作者介入修改）
→ 04 交互优化（状态/动效/边界，真机验收驱动）
→ Evaluator 验收 → 反哺（Taste 沉淀 / Eagle 回流 / 规则修订提案）
```

## 第五章 评价机制 —— Design Evaluator `骨架待填`

- `design/Evaluator.md`：跨项目通用验收基线（可判错条目）+ 巡检节奏（每轮交付必跑 vs 里程碑抽检，待定 D9）
- 项目 EXECUTION-CONTRACT 承接项目特有验收项

## 第六章 对比验证 —— 规则有没有用，实验说话 `方法初稿`

- 同一任务两遍：A 组无规则（独立会话）、B 组全量介入（规则 + design/ 六文件 + Eagle 引用）
- **介质升级**：两组产出都落在可视介质（Figma 双页 / HTML 双版），作者**盲评**更直观
- 判据草案：① Evaluator 清单通过率 ② Craft 反例命中数 ③ 到「作者可接受」的迭代轮数 ④ 盲评 taste 分
- 首个实验候选：cinema-caption 下带 hover 展开面板
- 结果记 `bAI/bAI/notes/`，结论回填本体系

## 第七章 进化 —— 本规则如何修改 `初稿`

- 修订触发：Taste 沉淀、对比实验结论、新素材（文章/案例/skill 入 Eagle 后的启发）
- 权限：第二、三章需作者确认；一、四、五章 AI 提案 + 作者复核；六、七章 AI 可直接补
- 每次修订更新版本号与本记录
